# Планировщик ёмкости — серверная версия

Многопользовательское веб-приложение для планирования ёмкости ресурсов по версиям (вехам) проектов.
Выросло из однофайлового планировщика: внешний вид и вся прежняя функциональность сохранены,
добавлены сервер, проекты, пользователи и права, автосохранение, Undo/Redo, загрузка конфигурации с
разрешением конфликтов, отвязка версий, закрытие вех, статусы задач и отчёт о готовности по дням с выгрузкой в PDF.

Полное описание и инструкции — в [DOC.md](DOC.md).

## Установка с GitHub

Нужны **git** и **Node.js 18+** (проверено на 26.x). Нативных модулей нет — работает одинаково на Windows, Linux и macOS.
Репозиторий не содержит данных и настроек конкретной установки: после установки приложение пустое.

**Linux / macOS**
```bash
git clone https://github.com/insideside/capacity-planner.git
cd capacity-planner
./install.sh
./start.sh
```

**Windows** (PowerShell или cmd)
```powershell
git clone https://github.com/insideside/capacity-planner.git
cd capacity-planner
install.bat
start.bat
```

`install` делает следующее:
- ставит зависимости;
- создаёт `config.json` из `config.example.json`;
- создаёт `.env` со случайным `SESSION_SECRET` и паролем первичного администратора — пароль печатается в конце установки.

Откройте **http://localhost:3000**, войдите как `admin` и смените пароль. Затем создайте проект («+ Проект»)
или загрузите конфигурацию («📂 Загрузить конфигурацию»).

Репозиторий публичный, поэтому для установки и обновления авторизация на GitHub не нужна.
Скрипт можно запустить и без предварительного клона — тогда он склонирует репозиторий сам:
`bash install.sh [каталог]`, на Windows — `.\install.ps1 [каталог]`.

**Обновление** — в приложении, кнопка «⟳ Обновление» (только администратор): показывает новые коммиты,
обновляет код и перезапускает сервер. Данные, `config.json` и `.env` при этом не затрагиваются.
Вручную: `./stop.sh && git pull --ff-only && npm ci --omit=dev && ./start.sh`.

## Запуск и остановка

| ОС | Запуск | Остановка |
|---|---|---|
| Linux / macOS | `./start.sh` (или `./start.sh -f` — на переднем плане) | `./stop.sh` |
| Windows (cmd) | `start.bat` | `stop.bat` |
| Windows (PowerShell) | `.\start.ps1` (или `.\start.ps1 -f`) | `.\stop.ps1` |
| Любая ОС вручную | `npm install && npm start` | `Ctrl+C` |

При первом запуске скрипты сами ставят зависимости. После старта откройте **http://localhost:3000**.

Первичный администратор — логин `admin`. Пароль берётся из `ADMIN_INITIAL_PASSWORD`; если переменная
не задана, временный пароль печатается в лог (`logs/server.log`). При первом входе пароль нужно сменить.

## Настройки

Основной файл настроек — **`config.json`** в корне. В git его нет: он создаётся из `config.example.json`
при установке или при первом запуске. Порт по умолчанию — **3000**.

```json
{
  "port": 3000,
  "host": "0.0.0.0",
  "dataDir": "./data",
  "sessionTtlHours": 12,
  "secureCookies": false,
  "trustProxy": false,
  "maxUploadMb": 5,
  "login": { "maxAttempts": 10, "windowMinutes": 15 },
  "reopenRequiresAdmin": false,
  "detachRemoveInactiveInSource": false,
  "pollIntervalSec": 10,
  "updateRestart": "self"
}
```

Переменные окружения (или файл `.env`, пример — `.env.example`) имеют приоритет над `config.json`:
`PORT`, `DATA_DIR`, `SESSION_SECRET`, `ADMIN_INITIAL_PASSWORD`, `HOST`, `SECURE_COOKIES`, `TRUST_PROXY`, `CONFIG_FILE`.

## Проверки

```bash
npm test             # 32 автотеста (без локального сида — 31, на синтетическом проекте): контрольные числа сида, отвязка, дифф/мёрдж, закрытие вех, API, права, 409
npm run verify-seed  # только контрольные числа сида (раздел 5 ТЗ)
```

Контрольные числа также проверяются при каждом старте сервера (строка `[seed] автопроверка сида: OK` в логе).

## Принятые решения

- **Стек:** Node.js + Express, клиент — исходный vanilla-JS без фреймворков. Пользователи и сессии хранятся
  в JSON-файлах (`DATA_DIR/users.json`, `sessions.json`), а не в SQLite: так нет нативных модулей и сборки
  под каждую ОС. Пароли хешируются bcrypt (`bcryptjs`, чистый JS, cost 12).
- **Формула ёмкости** взята из исходного файла без изменений: `рабочие дни окна × (% загрузки / 100) × 8 ч`.
  Поле «штат» (`n`) в расчёт не входит — `%` задаёт суммарную загрузку команды (например, 3 человека → 200 %).
  В ТЗ формула описана как «штат × % × дни», но источником истины по ТЗ является файл. Рабочие дни
  считаются в UTC, поэтому результат не зависит от часового пояса браузера или сервера.
- **Синхронизация связанных версий** ищет задачу-двойника **по WBS** (идентичность задач — по WBS), а если
  такого WBS в связанной версии нет — по имени, как в исходной версии. В сиде есть повторяющиеся имена
  («т. документация», «Ниокр. Синтетические нагрузочные испытания»): при поиске только по имени галочка
  могла бы уйти не той задаче.
- **Отвязка версий** — по буквальному правилу 4.7. Задачи, снятые в B и **не активные** в A (например, `rel:"off"`),
  по умолчанию **остаются**. Удалять ли и их, настраивается: флажок в окне отвязки и `detachRemoveInactiveInSource` в `config.json`.
  Удаляются только строки-итоги, у которых **были** листья и после удаления **не осталось** ни одного.
  Связь снимается с обеих сторон. Прежняя кнопка «✂ Связь» (снять связь без удаления задач) сохранена.
- **Закрытая веха** неизменяема на сервере: запрещены правки задач, галочек, ресурсов, дат, имени и связи.
  Удалить её тоже нельзя. Настройки отображения (свёртка, фильтры, ширина колонок) менять можно.
  Синхронизация из связанной открытой версии в закрытую не выполняется. Переоткрыть может редактор
  или администратор, а при `reopenRequiresAdmin: true` — только администратор.
- **Undo/Redo** работает на снимках данных проекта, до 100 шагов на сессию, и не учитывает свёртку и фильтры.
  Отмена тоже сохраняется на сервере как обычная правка. Если в проект подтягиваются чужие изменения
  (поллинг или слияние после 409), история отмены очищается: иначе Ctrl+Z мог бы молча откатить чужую работу.
- **Конкурентный доступ:** каждое сохранение передаёт `baseRevision`. На 409 клиент делает трёхстороннее
  слияние: непересекающиеся правки объединяются автоматически, а по пунктам, которые изменили оба,
  открывается окно выбора. Раз в `pollIntervalSec` секунд клиент проверяет ревизию на сервере.
- **Права на проекты:** создавать и удалять проекты может администратор, переименовывать — администратор и редактор.
- **Исправлены ошибки исходного кода**, которые портили данные:
  - удаление блока «1» удаляло и блоки «10», «11»…;
  - удаление задачи в связанной версии удаляло все задачи с тем же именем;
  - перенос блока в версию с теми же WBS создавал дубликаты WBS;
  - обработчики drag&drop накапливались при каждой перерисовке.
- **Миграция:** «Загрузить конфигурацию» принимает новый JSON, «голый» массив периодов из старой версии
  и HTML, сохранённый однофайловой версией (`CP_SAVED_STATE`). Так прежние данные можно перенести без потерь.
- **Статусы задач** хранятся в поле задачи `st` (`new` | `wip` | `done`; отсутствие = `new`). Готовность релиза
  считается только по отмеченным задачам, в % по часам и по задачам. Фаза («Разработка» / «Тестирование»)
  определяется окном ресурса задачи. Статус синхронизируется с задачей-двойником связанной версии.
  В CSV-экспорт добавлена колонка `status`; старые CSV без неё по-прежнему импортируются.
  Отчёт — отдельная страница `/report.html` с печатью в PDF (A4, книжная).
- **Отчёт по дням** строится по датам задач: `ws` (начато) и `dn` (выполнено), формат `YYYY-MM-DD`;
  даты проставляются при смене статуса и правятся в окне редактирования. План — равномерное выполнение
  объёма по рабочим дням окна. Прогноз — по темпу последних 10 рабочих дней.
  Выполненные задачи без даты относятся на начало окна.
- Кнопки «💾 Сохранить» / «📂 Загрузить» стали «Скачать / Загрузить конфигурацию». «↺ Сбросить» возвращает
  данные текущего проекта к стартовым; действие можно отменить.
