## 1. Что это

Веб-приложение для планирования ёмкости ресурсов команды по версиям (релизам, вехам).
Для каждой версии задаётся список задач с оценками в часах и назначенными ресурсами, окна разработки
и тестирования и пул ресурсов. Программа считает загрузку каждого ресурса и сравнивает её с ёмкостью.

Приложение ставится на сервер, в нём одновременно работают несколько пользователей. Все данные хранятся
на сервере, и каждое изменение сохраняется сразу.

## 2. Функциональность

### 2.1. Проекты

Иерархия данных: **Проект → Версии (периоды, вехи) → Задачи и ресурсы.**

- Проектов может быть сколько угодно; переключатель — в верхней панели («Проект: …»).
- Каждый проект хранится на сервере отдельным файлом `DATA_DIR/projects/<id>.json`. Формат этого файла
  совпадает с тем, что скачивается кнопкой «Скачать конфигурацию».
- Администратор создаёт (пустым или копией стартовых данных) и удаляет проекты. Переименовать проект
  могут администратор и пользователи с правом редактирования.
- Ссылка вида `http://сервер:3000/#p=<id>` открывает конкретный проект.

### 2.2. Версии (периоды)

У версии есть название, окно разработки, окно тестирования, пул ресурсов и список задач.

- **Добавить период** — кнопка внизу страницы. Новый период можно сразу связать с существующим (см. 2.5).
- Название редактируется прямо в заголовке; клик по заголовку сворачивает и разворачивает версию.
- `✕` в заголовке удаляет версию.
- При прокрутке сверху закрепляется шапка версии с загрузкой ресурсов (клик по ресурсу — фильтр).

### 2.3. Задачи

- Иерархия: **строки-итоги** (блоки) и **листья** (задачи). Уникальный ключ задачи — **WBS** (например, `2.1.7`).
  Имена задач могут повторяться.
- Галочка — включить задачу в расчёт. Галочка блока переключает все его листья.
- В строке задачи можно править часы и ресурс. Двойной клик по названию открывает окно редактирования:
  переименование, смена родителя, превращение в блок и обратно, копирование или перенос в другую версию.
- «+ Задача» и «+ Блок» добавляют строки; `+` в строке блока добавляет задачу в этот блок.
- Перетаскивание строк меняет порядок и вложенность.
- Фильтры: по ресурсу и по активности («✓ Активные» / «✗ Неактивные»). Блоки сворачиваются кнопками ▼/▶.
- Ширину колонок «Ч» и «Ресурс» можно менять мышью.
- `❗` — задача активна сразу в нескольких версиях. Бейджи справа от названия показывают, в какой из
  связанных версий задача активна (красный бейдж — в обеих).

### 2.4. Ресурсы и расчёт ёмкости

У ресурса есть ключ (например, `core`), название, штат (чел.), % загрузки, окно («Разработка» или
«Тестирование») и цвет.

- **Ёмкость** = рабочие дни окна × (% загрузки / 100) × 8 ч. Рабочие дни — будни без праздников из
  встроенного календаря на 2026–2027 годы. `%` — суммарная загрузка команды ресурса (например, 3 разработчика
  с загрузкой около 67 % каждый дают 200 %). Штат указывается справочно.
- **Загрузка** = сумма часов отмеченных листьев, назначенных на ресурс.
- В карточке ресурса отображаются `загрузка / ёмкость` и остаток (✅) или перегрузка (❌).
  Полоса становится оранжевой при загрузке больше 85 % и красной при перегрузке.
- Справа — итоги (часы и задачи), загрузка по ресурсам и таблица по блокам (Ядро / Тест / Прочее).
- «+ Ресурс» добавляет ресурс, `✕` на карточке удаляет его (задачи ресурса станут «без ресурса»).
- **«⇉ Штат в открытые версии»** копирует штат и % загрузки ресурсов этой версии во все **открытые** версии.
  Закрытые вехи при этом не меняются.

### 2.4a. Статусы задач и готовность релиза

- У каждой задачи-листа есть **статус**: **Новое**, **В работе** или **Выполнено**. Он выбирается в колонке
  «Статус» справа от названия задачи. Выполненные задачи зачёркнуты.
- В строке блока показаны полоса и счётчик «выполнено / всего» по отмеченным задачам блока.
- Статус — свойство самой работы, поэтому он переносится и в задачу-двойника связанной версии.
  Смена статуса сохраняется на сервере и отменяется через Ctrl+Z, как любая правка.
- Карточка **«Готовность релиза»** в правой панели считается динамически по задачам, включённым в релиз
  (отмеченным галочкой). Она показывает:
  - % выполнения по часам и по задачам;
  - полосу «выполнено / в работе / не начато»;
  - количество задач и часов в каждом статусе.
- **Фильтры готовности:** «Все», «Разработка», «Тестирование». Фаза задачи определяется окном её ресурса:
  «Разработка» или «Тестирование» в карточке ресурса. Задачи без ресурса учитываются только в «Все».
  На кнопках фильтров сразу виден % готовности каждой фазы.
- У закрытой вехи статусы, как и остальные данные, не меняются.
- **Даты.** При переводе в «В работе» запоминается дата начала, при переводе в «Выполнено» — дата выполнения
  (сегодня). Возврат в «Новое» стирает обе даты. Даты можно поправить в окне редактирования задачи
  (двойной клик): поля «начато» и «выполнено». По датам выполнения строится отчёт по дням.
  Задачи, отмеченные выполненными до появления дат, считаются «выполненными без даты» и относятся на начало окна.
- В карточке под процентами — строка **по дням**: отставание или опережение плана в рабочих днях,
  сколько рабочих дней осталось до конца окна и прогноз даты завершения.

**Отчёт о выполнении** открывается кнопкой «📄 Отчёт» в карточке готовности. Это отдельная страница
`/report.html`; она печатается в PDF отдельно от планировщика: кнопка «⬇ PDF», формат A4, книжная ориентация.
Отчёт содержит:
- заголовок: проект, версия, окна разработки и тестирования, время формирования, ревизия данных;
- готовность по фазам: «Разработка» и «Тестирование» рядом, выбранная фаза подсвечена;
- раздел **«По дням»** — идёт первым:
  - **отставание / опережение** в рабочих днях. Это разница между днём равномерного плана, которому
    соответствует фактически выполненный объём, и сегодняшним рабочим днём;
  - **рабочих дней осталось** из общего числа дней окна;
  - **нужный темп** (ч на рабочий день, чтобы успеть к концу окна) против фактического: за последние
    10 рабочих дней и в среднем с начала окна;
  - **прогноз завершения** по темпу последних 10 рабочих дней (если он нулевой — по среднему):
    «в срок» или «позже окна»;
  - график **накопленного выполнения** (факт против равномерного плана по рабочим дням), с отметками
    «сегодня» и «конец окна»; при наведении показывает значения за день;
  - график **выполненных часов по дням** с линией нужного темпа;
  - **таблица по дням**: задачи и часы за день, накопленные часы, факт и план в %, отклонение от плана в часах
    и названия задач, выполненных в этот день. Флажок «все рабочие дни в таблице» показывает и дни без выполнения.

  Окно для расчёта зависит от фильтра: «Разработка» — окно разработки, «Тестирование» — окно тестирования,
  «Все» — от самого раннего начала до самого позднего конца. Праздники берутся из того же календаря,
  что и ёмкость;
- показатели: % по часам, % по задачам, в работе, не начато; общую полосу выполнения;
- таблицы «По ресурсам» и «По блокам»: задач, выполнено, в работе, новые, часы, % по часам;
- списки задач по блокам: «В работе», «Не начато» и по желанию «Выполнено».

На панели отчёта можно сменить версию и фильтр готовности: «Все задачи», «Разработка» или «Тестирование».
Фильтр, выбранный в карточке планировщика, передаётся в отчёт. Отчёт сам перечитывает данные, когда проект
меняется на сервере (раз в `pollIntervalSec` секунд), поэтому всегда актуален. Отчёт доступен и пользователям
с правом «чтение». Ссылку на отчёт (`/report.html#p=<проект>&v=<версия>&f=dev|tst`) можно передать коллеге
с доступом к проекту.

### 2.5. Связанные версии

Две версии можно связать: например, 3.2.2 ↔ 3.2.3 в стартовом проекте. Связанные версии используют общий
мастер-список задач и отличаются только галочками.

- Если отметить задачу в одной версии, в связанной она снимается, и наоборот.
- Правка часов, ресурса и имени задачи переносится в задачу-двойника. Двойник ищется по WBS, а если такого
  WBS в связанной версии нет — по имени.
- Новая задача добавляется в обе версии; в связанной она снята.
- Удаление задачи удаляет и её двойника.
- Поле `rel` у задачи — признак релиза из исходных данных: `"322"`, `"323"` или `"off"`.
- «✂ Связь» снимает связь и оставляет задачи как есть.

### 2.6. Отвязка версий

**«⛓ Отвязать»** в заголовке связанной версии. В окне выбирается направление: «Отвязать B от A».

Правило:
1. Из **B** удаляется каждый лист `t`, который в B **снят** (`chk_B[t.w] === false`), если в **A** есть задача
   с тем же WBS и она **активна** (`chk_A[t.w] === true`).
2. После этого удаляются строки-итоги B, у которых были листья, а теперь не осталось ни одного.
3. Связь снимается с обеих сторон, и B становится независимой.

Задачи, снятые в B и **не активные в A** (например, задача с `rel:"off"`) или отсутствующие в A, по умолчанию
**остаются** в B. Окно отвязки показывает их отдельным списком. Флажок «Также удалить снятые задачи, которые не
активны в исходной версии» удаляет и их; значение флажка по умолчанию задаёт `detachRemoveInactiveInSource`.

Перед подтверждением окно показывает, сколько задач и часов будет удалено и какие задачи останутся.
Операцию можно отменить (Ctrl+Z).

Пример на стартовых данных: после отвязки 3.2.3 от 3.2.2 в 3.2.3 удаляются 112 задач (все активные в 3.2.2).
Остаются 74 отмеченные задачи (3003 ч) и снятая off-задача «Добавление в ЦМ фильтров по группам».

### 2.7. Закрытие вехи

**«🔒 Закрыть»** в заголовке версии.

- Версия получает признак `closed: true` и снимок `frozenSnapshot`: рабочие дни, пул ресурсов, ёмкость
  и загрузка по каждому ресурсу, итоги, дата и автор закрытия.
- Закрытая веха доступна **только для чтения**. Нельзя менять задачи, галочки, ресурсы, даты, название
  и связь, нельзя удалить саму веху. Запрет проверяется и в интерфейсе, и на сервере. Сворачивать блоки
  и пользоваться фильтрами можно.
- Цифры ресурсов берутся из снимка и **не пересчитываются**, даже если изменились праздничный календарь
  или формула. Действие «Штат в открытые версии» закрытые вехи не трогает. Из связанной открытой версии
  галочки в закрытую не синхронизируются.
- Закрытая веха помечена бейджем «🔒 Закрыта <дата>» и строкой «❄ Ресурсы заморожены…», её карточка приглушена.
- **«🔓 Переоткрыть»** снимает признак и возвращает пересчёт. По умолчанию доступно редактору и администратору,
  при `reopenRequiresAdmin: true` — только администратору.
- Закрытие и переоткрытие можно отменить (Ctrl+Z).

### 2.8. Конфигурация: скачивание и загрузка

- **«💾 Скачать конфигурацию»** скачивает JSON проекта:
  ```json
  {
    "schema": "capacity-planner/v1",
    "projectId": "…", "name": "Релиз 2026", "revision": 42, "updatedAt": "2026-10-02T10:00:00.000Z",
    "periods": [ { "id": "p1", "name": "3.2.2", "devStart": "2026-06-01", "devEnd": "2026-11-06",
                   "tstStart": "2026-07-01", "tstEnd": "2026-12-20",
                   "res": { "core": { "label": "Разработчики ядра", "n": 3, "pct": 200, "period": "dev", "color": "#2255e2" } },
                   "tasks": [ { "w": "1.1", "n": "…", "h": 80, "r": "core", "s": false, "d": 1, "rel": "322", "st": "done", "ws": "2026-09-21", "dn": "2026-09-30" } ],
                   "chk": { "1.1": true }, "linkedTo": "p2", "closed": false,
                   "collapsed": {}, "filter": null, "filterActive": null, "folded": false, "colWidths": { "cb": 32, "h": 46, "r": 98, "name": 0, "del": 18 } } ]
  }
  ```
- **«📂 Загрузить конфигурацию»** принимает:
  - JSON этого формата;
  - «голый» массив периодов из старой версии;
  - HTML однофайловой версии планировщика:
    - **исходный** файл (например, `capacity_planner-000.html`): данные берутся из `IMPORTED_RES`,
      `IMPORTED_TASKS` и `IMPORTED_DATES_<rel>`; для каждого `rel` создаётся версия (`322` → «3.2.2»)
      с галочками по полю `rel`, и две такие версии связываются, как в исходном планировщике;
    - файл, **сохранённый** кнопкой «💾 Сохранить»: данные берутся из `CP_SAVED_STATE`.

    Код из HTML-файла не выполняется: литералы данных читаются как текст. Если в файле вместо данных
    стоит выражение, загрузка отклоняется.

  Чтобы перенести данные из исходного HTML: «📂 Загрузить конфигурацию» → «Как новый проект» → выберите файл.

  Файл проверяется по схеме (типы, даты, уникальность WBS, ключи ресурсов, цвета) и по размеру (`maxUploadMb`).
- Режим **«Как новый проект»** (только администратор) создаёт новый проект без конфликтов.
- Режим **«Поверх текущего проекта»** ничего не затирает: открывается окно разрешения конфликтов (2.9).
- «⬆ Импорт CSV» и «⬇ Экспорт CSV» работают как в исходной версии. Полный CSV-импорт заменяет все версии
  проекта, поэтому недоступен, пока в проекте есть закрытые вехи. «⬇ PDF» печатает страницу (A4, альбомная).

### 2.9. Окно разрешения конфликтов

Сущности файла и текущего проекта сопоставляются так:
- версии — по `id`, а если такого нет — по названию;
- задачи — по WBS;
- ресурсы — по ключу.

Каждое различие попадает в одну из категорий:

| Статус | Смысл | «Текущее» | «Из файла» |
|---|---|---|---|
| **Добавлено** | есть только в файле | не добавлять | добавить |
| **Удалено** | есть только в текущем | оставить | удалить |
| **Изменено** | отличаются поля | оставить как есть | взять значения из файла |

- Для изменённой задачи показываются конкретные поля: название, часы, ресурс, `rel`, статус, галочка, признак
  строки-итога, уровень. Для ресурса — название, штат, %, окно, цвет. Для версии — её даты, название, связь
  и статус «закрыта».
- Отдельными пунктами идут «Порядок задач», «Порядок версий» и (по флажку) служебные настройки отображения.
- Пункты сгруппированы по версиям. Выбор можно сделать по каждому пункту (клик по ячейке),
  для всех пунктов версии («все в группе: …») или для всего файла сразу («Всё — текущее» / «Всё — из файла»).
- Пункты без различий не показываются и остаются как есть.
- После «Применить» сервер собирает итоговое состояние и сохраняет его новой ревизией.
  Загрузку можно отменить (Ctrl+Z).

То же окно открывается при **одновременном редактировании** (2.11): колонки называются «На сервере» и «Мои изменения».

### 2.10. Пользователи и права

- **Администратор** имеет полный доступ ко всем проектам и управляет пользователями.
- **Пользователь** получает права на каждый проект отдельно: **нет доступа**, **чтение** или **редактирование**.
  Проект без доступа не виден в списке, а его API отвечает 404.
- Права проверяются на сервере при каждом запросе. В режиме «только чтение» поля ввода заблокированы,
  кнопки изменений скрыты, статус показывает «👁 Только чтение».
- Первичный администратор (`admin`) создаётся при первом запуске с паролем из `ADMIN_INITIAL_PASSWORD`
  и должен сменить пароль при первом входе. Новые пользователи и пользователи, чей пароль сбросил
  администратор, тоже меняют пароль при входе.
- Пароли хранятся только в виде bcrypt-хеша. Сессия передаётся в cookie `httpOnly; SameSite=Strict`
  (`Secure` при `secureCookies: true`). Запросы защищены CSRF-токеном. Вход ограничен: не больше
  `login.maxAttempts` попыток за `login.windowMinutes` минут на IP и на логин.

### 2.11. Автосохранение и одновременная работа

- Каждое изменение сразу отправляется на сервер. Серия быстрых правок группируется примерно за 300 мс,
  поэтому правка в поле ввода сохраняется, даже если поле не потеряло фокус.
- Статус в верхней панели: «⏳ Сохранение…», «✓ Сохранено · ред. N», «⚠ Нет связи с сервером — повтор…».
  При потере связи данные остаются в памяти страницы, и сохранение повторяется. Если закрыть вкладку
  с несохранёнными изменениями, браузер предупредит.
- Каждое сохранение передаёт номер ревизии, от которой отталкивался клиент. Если на сервере ревизия новее,
  сервер отвечает 409 и присылает свежую версию. Клиент объединяет изменения сам:
  - правки разных пунктов объединяются молча, с уведомлением;
  - если один пункт изменили оба пользователя, открывается окно выбора «На сервере / Мои изменения».

  Изменения не теряются молча.
- Раз в `pollIntervalSec` секунд (и при возврате на вкладку) клиент проверяет ревизию и подтягивает
  чужие изменения.
- localStorage, sessionStorage и кэш браузера для данных не используются.

### 2.12. Отмена и повтор

- **Ctrl+Z** (⌘Z) — отменить, **Ctrl+Shift+Z** или **Ctrl+Y** — повторить. Те же действия есть на кнопках в панели.
- Отменяются все изменения данных, включая загрузку конфигурации со слиянием, отвязку версий,
  закрытие и переоткрытие вех, сброс, импорт CSV и удаление версий.
- Результат отмены или повтора сохраняется на сервере как обычное изменение.
- Свёртка блоков, фильтры и ширина колонок в историю не попадают.
- Когда в проект подтягиваются изменения другого пользователя, история отмены очищается, чтобы Ctrl+Z
  не откатил чужую работу.

## 3. Установка и запуск

### 3.1. Требования

- Node.js **18 или новее** (LTS): https://nodejs.org. npm входит в комплект.
- **git** — для установки и обновления из репозитория.
- Сборка нативных модулей не нужна. Windows, Linux и macOS поддерживаются одинаково.

### 3.1a. Установка с GitHub

Репозиторий: **https://github.com/insideside/capacity-planner** (публичный). В нём только код и документация.
Данные проектов, пользователи, `config.json`, `.env` и стартовые данные в репозиторий не входят,
поэтому после установки приложение пустое.

| ОС | Установка | Запуск |
|---|---|---|
| Linux / macOS | `git clone https://github.com/insideside/capacity-planner.git && cd capacity-planner && ./install.sh` | `./start.sh` |
| Windows | `git clone https://github.com/insideside/capacity-planner.git`, затем `cd capacity-planner` и `install.bat` | `start.bat` |

Репозиторий публичный: для клонирования и обновления из приложения авторизация на GitHub не нужна,
серверу достаточно доступа в интернет к github.com по HTTPS.

Что делает установщик (`install.sh`, `install.ps1`, `install.bat`):
1. Проверяет наличие git, Node.js 18+ и npm.
2. Работает внутри клона, если запущен из него. Иначе клонирует репозиторий в указанный каталог
   (по умолчанию `capacity-planner`), а если клон там уже есть — обновляет его (`git pull --ff-only`).
   Адрес и ветку можно переопределить переменными `CP_REPO_URL` и `CP_BRANCH`.
3. Ставит зависимости (`npm ci --omit=dev` — ровно по `package-lock.json`).
4. Создаёт `config.json` из `config.example.json`, если его нет.
5. Создаёт `.env`, если его нет: случайный `SESSION_SECRET` и пароль первичного администратора.
   Пароль берётся из `ADMIN_INITIAL_PASSWORD`, если переменная задана, иначе генерируется
   и печатается в конце установки.

Существующие `config.json`, `.env` и `data/` установщик не трогает, поэтому повторный запуск безопасен.

После установки:
1. Запустите сервер скриптом start.
2. Войдите как `admin` и смените пароль.
3. Создайте проект («+ Проект») или загрузите конфигурацию из файла («📂 Загрузить конфигурацию → Как новый проект»).

Стартовые данные из однофайлового планировщика по желанию генерируются локально — см. `seed/README.md`.

### 3.1b. Обновление из приложения

Кнопка **«⟳ Обновление»** в верхней панели видна только администратору. В окне показаны:
- текущая версия (номер и коммит);
- ветка и её upstream;
- список новых коммитов в репозитории.

«Обновить и перезапустить» по шагам:
1. Сохраняет несохранённые изменения пользователя.
2. Получает код: `git fetch` и fast-forward до upstream (`git merge --ff-only`).
3. Если изменились `package.json` или `package-lock.json`, выполняет `npm ci --omit=dev`. Если установка
   зависимостей не удалась, код откатывается к прежнему коммиту, и приложение продолжает работать на старой версии.
4. Перезапускает сервер. Страница перезагрузится сама, сессии сохраняются.

Обновление не выполняется (окно объяснит причину), если:
- приложение установлено не из git;
- у ветки не настроен upstream;
- файлы приложения изменены локально;
- в локальной ветке есть свои коммиты.

Такие случаи решаются вручную. Данные (`DATA_DIR`), `config.json` и `.env` в git не хранятся
и обновлением не затрагиваются.

Способ перезапуска задаёт `updateRestart` в `config.json`:
- `"self"` (по умолчанию) — сервер сам запускает новый процесс, лог пишется в `logs/server.log`.
  Подходит для запуска скриптами start и stop.
- `"exit"` — сервер просто завершается, а запускает его заново супервизор (systemd с `Restart=always`, pm2,
  служба Windows). Используйте этот вариант при работе под systemd: см. раздел 7.

Обновить вручную: `./stop.sh && git pull --ff-only && npm ci --omit=dev && ./start.sh`
(на Windows — те же команды со `stop.bat` и `start.bat`).

### 3.2. Скрипты

| ОС | Запуск | Остановка | Примечание |
|---|---|---|---|
| Linux / macOS | `./start.sh` | `./stop.sh` | `./start.sh -f` — на переднем плане |
| Windows, cmd / двойной клик | `start.bat` | `stop.bat` | вызывают `start.ps1` / `stop.ps1` |
| Windows, PowerShell | `.\start.ps1` | `.\stop.ps1` | `.\start.ps1 -f` — на переднем плане |
| Любая ОС | `npm install` → `npm start` | `Ctrl+C` | вручную |

Что делают скрипты:
- **Запуск:**
  - при первом запуске ставит зависимости (`npm ci --omit=dev`);
  - запускает сервер в фоне;
  - пишет лог в `logs/server.log`;
  - печатает адрес, например `http://localhost:3000`.

  Сервер записывает PID в `capacity-planner.pid`. Если сервер уже запущен, повторный запуск ничего не делает.
- **Остановка:** завершает процесс по PID-файлу, а если файла нет — ищет процесс на порту из настроек.

Если скрипт `.sh` не запускается, выполните `chmod +x start.sh stop.sh`. Если PowerShell блокирует скрипты,
запускайте через `.bat`: он вызывает PowerShell с `-ExecutionPolicy Bypass`.

### 3.3. Первый запуск

1. Установщик уже задал пароль администратора и `SESSION_SECRET` в `.env`. Без установщика:
   - скопируйте `.env.example` → `.env` и задайте `ADMIN_INITIAL_PASSWORD` и `SESSION_SECRET`;
   - если пароль не задан, сервер сгенерирует временный и напечатает его в лог;
   - если не задан `SESSION_SECRET`, секрет сгенерируется и сохранится в `DATA_DIR/session-secret.key`.
2. Запустите сервер, откройте адрес, войдите как `admin` и смените пароль.
3. Создайте первый проект.
4. Если в `seed/` лежат стартовые данные (см. `seed/README.md`), при первом запуске из них автоматически
   создаётся проект. Сервер проверяет его контрольные числа; в логе должна быть строка `[seed] автопроверка сида: OK`.

## 4. Настройка

Файл **`config.json`** в корне приложения. В git он не хранится: создаётся из `config.example.json`
установщиком или при первом запуске. Другой файл можно указать через `CONFIG_FILE`.

| Параметр | По умолчанию | Описание |
|---|---|---|
| `port` | `3000` | порт HTTP-сервера |
| `host` | `0.0.0.0` | адрес прослушивания; `127.0.0.1` — только локально, например за nginx |
| `dataDir` | `./data` | каталог данных |
| `sessionTtlHours` | `12` | время жизни сессии (продлевается при активности) |
| `secureCookies` | `false` | ставить флаг `Secure` у cookie; включайте при работе по HTTPS |
| `trustProxy` | `false` | доверять `X-Forwarded-For` (за reverse-proxy: `1`) — для корректного rate-limit |
| `maxUploadMb` | `5` | максимальный размер загружаемой конфигурации |
| `login.maxAttempts` / `login.windowMinutes` | `10` / `15` | ограничение попыток входа |
| `reopenRequiresAdmin` | `false` | переоткрывать вехи может только администратор |
| `detachRemoveInactiveInSource` | `false` | значение по умолчанию флажка «удалять также неактивные в исходной» |
| `pollIntervalSec` | `10` | как часто клиент проверяет изменения на сервере |
| `updateRestart` | `"self"` | перезапуск после обновления из git: `"self"` — сам, `"exit"` — через супервизор (systemd/pm2) |

Переменные окружения и `.env` имеют приоритет над файлом: `PORT`, `HOST`, `DATA_DIR`, `SESSION_SECRET`,
`ADMIN_INITIAL_PASSWORD`, `SECURE_COOKIES`, `TRUST_PROXY`, `CONFIG_FILE`.

## 5. Работа с программой

### Завести проект
1. Нажмите «+ Проект» (только администратор), введите название и выберите содержимое: пустой проект
   или копия «Релиз 2026» (если установлены стартовые данные, см. `seed/README.md`).
2. Чтобы перенести данные из файла, нажмите «📂 Загрузить конфигурацию» и выберите «Как новый проект».

### Завести пользователей и права
1. Откройте «👥 Пользователи».
2. В блоке «Новый пользователь» введите логин и пароль (не короче 8 символов), выберите роль и нажмите «Создать».
3. В строке пользователя для каждого проекта выберите «нет доступа», «чтение» или «редактирование».
   Изменение применяется сразу.
4. «🔑 Пароль» задаёт новый пароль, пользователь сменит его при входе. `✕` удаляет пользователя.
   Удалить себя или последнего администратора нельзя.

### Экспорт и импорт конфигурации
- Чтобы сделать резервную копию проекта или передать его, нажмите «💾 Скачать конфигурацию».
- Чтобы загрузить изменения из файла: «📂 Загрузить конфигурацию» → «Поверх текущего проекта» →
  разберите различия в окне конфликтов (2.9) → «Применить».

### Как читать окно конфликтов
- Сверху — общее число различий по статусам: Добавлено, Удалено, Изменено.
- Группы соответствуют версиям проекта. В каждой строке:
  - статус;
  - пункт: задача (WBS и название), ресурс, поле версии или порядок;
  - две колонки со значениями и вариантом выбора.
- Подсвеченная ячейка — выбранный вариант. Клик по другой ячейке меняет выбор.
- В колонках показаны только отличающиеся поля, например «Часы: 40 ч» → «Часы: 80 ч».
- Для пункта «Добавлено» в колонке «Текущее» стоит «— отсутствует —», выбор этой ячейки означает «не добавлять».
  Для пункта «Удалено» так же устроена колонка «Из файла»: её выбор означает «удалить».

### Как отвязать версию
1. В заголовке связанной версии нажмите «⛓ Отвязать».
2. Выберите направление: «Отвязать «3.2.3» от «3.2.2»».
3. Проверьте список удаляемых задач и список задач, которые останутся. При необходимости отметьте
   флажок про неактивные задачи.
4. Нажмите «Отвязать». Если передумали — Ctrl+Z.

### Как закрыть или переоткрыть веху
- «🔒 Закрыть» → «Подтвердить». Версия станет только для чтения с замороженными ресурсами.
- «🔓 Переоткрыть» → «Подтвердить». Пересчёт ёмкости возобновится.

### Сменить пароль и выйти
«🔑» в правом верхнем углу — смена пароля, «Выйти» — завершение сессии.

## 6. Резервное копирование

Все данные лежат в `DATA_DIR` (по умолчанию `./data`):

```
data/
  projects/<id>.json      текущие конфигурации проектов (тот же формат, что «Скачать конфигурацию»)
  history/<id>/<rev>.json последние 50 ревизий каждого проекта — для ручного восстановления
  trash/                  удалённые проекты
  users.json              пользователи (хеши паролей) и права
  sessions.json           активные сессии
  session-secret.key      секрет подписи cookie (если SESSION_SECRET не задан)
```

- Каталог можно копировать на ходу: запись атомарная (временный файл + переименование).
  Для гарантированно согласованной копии остановите сервер.
  - Linux/macOS: `tar czf backup-$(date +%F).tgz data/`
  - Windows (PowerShell): `Compress-Archive data backup.zip`
- Восстановление: остановите сервер, верните каталог `data/`, запустите сервер.
- Откат проекта к прошлой ревизии: скачайте или возьмите файл из `history/<id>/` и загрузите его через
  «Загрузить конфигурацию → Поверх текущего проекта», выбрав «Всё — из файла».

## 7. Развёртывание за nginx с HTTPS

`config.json`:
```json
{ "port": 3000, "host": "127.0.0.1", "secureCookies": true, "trustProxy": 1 }
```

`/etc/nginx/sites-available/capacity-planner`:
```nginx
server {
    listen 80;
    server_name planner.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    server_name planner.example.com;

    ssl_certificate     /etc/letsencrypt/live/planner.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/planner.example.com/privkey.pem;
    add_header Strict-Transport-Security "max-age=31536000" always;

    client_max_body_size 6m;   # чуть больше maxUploadMb

    location / {
        proxy_pass         http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header   Host              $host;
        proxy_set_header   X-Real-IP         $remote_addr;
        proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header   X-Forwarded-Proto $scheme;
    }
}
```

Сертификат: `sudo certbot --nginx -d planner.example.com`.

Автозапуск через systemd — `/etc/systemd/system/capacity-planner.service`:
```ini
[Unit]
Description=Capacity Planner
After=network.target

[Service]
WorkingDirectory=/opt/capacity-planner
ExecStart=/usr/bin/node server/index.js
Environment=NODE_ENV=production
EnvironmentFile=/opt/capacity-planner/.env
Restart=always
User=planner

[Install]
WantedBy=multi-user.target
```
`sudo systemctl enable --now capacity-planner`

При работе под systemd поставьте в `config.json` `"updateRestart": "exit"`. Тогда после обновления из
приложения сервер перезапустит systemd. Пользователь службы (`planner`) должен быть владельцем каталога
приложения и иметь доступ к репозиторию на чтение.

## 8. API

Все запросы, кроме входа, требуют cookie сессии. Изменяющие запросы требуют ещё заголовок `X-CSRF-Token`
(токен выдаёт `GET /api/auth/me` или `POST /api/auth/login`).

| Метод и путь | Права | Назначение |
|---|---|---|
| `POST /api/auth/login` `{login,password}` | — | вход |
| `POST /api/auth/logout` | вход | выход |
| `GET /api/auth/me` | вход | текущий пользователь, CSRF-токен, настройки клиента |
| `POST /api/auth/password` `{oldPassword,newPassword}` | вход | смена пароля |
| `GET/POST /api/users`, `PUT/DELETE /api/users/:id` | админ | пользователи, роли, права `{perms:{projectId:'read'\|'edit'}}` |
| `GET /api/projects` | вход | доступные проекты |
| `POST /api/projects` `{name, fromSeed?, project?}` | админ | создать (пустой / из сида / из файла) |
| `GET /api/projects/:id` | чтение | проект целиком |
| `GET /api/projects/:id/revision` | чтение | текущая ревизия (для сверки) |
| `PUT /api/projects/:id` `{baseRevision, periods?, name?}` | редакт. | сохранить; при устаревшей ревизии — **409** `{current}` |
| `DELETE /api/projects/:id` | админ | удалить (в корзину) |
| `GET /api/projects/:id/download` | чтение | скачать конфигурацию |
| `POST /api/projects/:id/upload` `{file}` | редакт. | проверить файл, вернуть дифф `{uploadId, items}` |
| `POST /api/projects/:id/merge` `{uploadId, baseRevision, choices}` | редакт. | применить выбор `{key:'cur'\|'file'}` |
| `POST /api/projects/:id/periods/:pid/detach` `{baseRevision, fromId, removeInactiveInSource?}` | редакт. | отвязать версию `pid` от `fromId` |
| `POST /api/projects/:id/periods/:pid/close` `{baseRevision}` | редакт. | закрыть веху |
| `POST /api/projects/:id/periods/:pid/reopen` `{baseRevision}` | редакт./админ | переоткрыть веху |
| `GET /api/seed` | вход | стартовые данные (для «Сбросить»); 404, если сид не установлен |
| `GET /api/admin/update` | админ | версия, ветка, новые коммиты в репозитории |
| `POST /api/admin/update` | админ | обновить код из git и перезапустить сервер |
